Weakness: Missing Authorization (CWE-862)

Asset in Scope: TiDB product, such as TiKV, TiDB, TiFlash, PD

1. Summary

TiDB gates every statistics-modifying statement behind a privilege check — ANALYZE TABLE, LOCK STATS, UNLOCK STATS and REFRESH STATS all verify privileges on thei
r target tables. LOAD STATS does not.

Because the target table is named inside the *loaded file* rather than in the statement, any authenticated user — including one holding no privileges whatsoever — can rep
lace the optimizer statistics of any table in the cluster, including tables they cannot read.

2. Root cause

Four statistics statements are dispatched adjacently in the plan builder (pkg/planner/core/planbuilder.go:628-634). Their builders:

// :4902 — LOAD STATS. No privilege check. Note the UNNAMED receiver: this function
//         structurally cannot call b.appendVisitInfo(...), so no privilege is ever recorded.
func (*PlanBuilder) buildLoadStats(ld *ast.LoadStatsStmt) base.Plan {
    p := &LoadStats{Path: ld.Path}
    return p
}

// :4907 — REFRESH STATS
func (b *PlanBuilder) buildRefreshStats(rs *ast.RefreshStatsStmt) (base.Plan, error) {
    ...
    b.requireSelectOrRestoreAdminPrivForStatsObjects(rs.RefreshObjects)   // :4912
}

// :4994 — LOCK STATS   ("requires INSERT and SELECT privilege ... same as buildAnalyze")
func (b *PlanBuilder) buildLockStats(ld *ast.LockStatsStmt) base.Plan {
    ...
    b.requireInsertAndSelectPriv(ld.Tables)                               // :4999
}

// :5005 — UNLOCK STATS -> b.requireInsertAndSelectPriv(ld.Tables)
// :3208 — ANALYZE      -> b.requireInsertAndSelectPriv(as.TableNames)

TiDB enforces privileges by having the planner append visitInfo, which CheckPrivilege later verifies. buildLoadStats appends none, so there is nothing to verify.

The executor adds no gate either — pkg/executor/load_stats.go, LoadStatsExec.Next() only checks that the path is non-empty and stores LoadStatsInfo in a session var
iable; Open() is a no-op.

No test or document in the repository asserts any privilege requirement for LOAD STATS.

4. What this is not

Stated explicitly so severity is not overestimated:

- Not a server-side arbitrary file read. pkg/server/conn.go:2431-2450 requires the client to advertise mysql.ClientLocalFiles and then calls cc.getDataFromPath
— the LOCAL INFILE path. The file is supplied by the client, so no server file is read. (The attacker controls their own client, so this is not a mitigation, but it i
s not a file-disclosure primitive either.)
- Not remote-unauthenticated. A valid session is required — but any session will do, including one with no grants.
- Not a denial-of-service report. The defect is the missing authorization check.

5. Suggested fix

Give buildLoadStats a named receiver and apply the same gate as its siblings:

func (b *PlanBuilder) buildLoadStats(ld *ast.LoadStatsStmt) base.Plan {
    p := &LoadStats{Path: ld.Path}
    // Loading statistics replaces optimizer metadata for the tables named in the
    // payload; require the same privileges as ANALYZE / LOCK STATS / UNLOCK STATS.
    b.requireInsertAndSelectPriv(/* tables named by the payload */)
    return p
}

Because the target tables are only known once the file is parsed, the check must be enforced where the payload is applied — LoadStatsInfo.Update() — verifying INSERT+SE
LECT on each table named in the file, and rejecting the load otherwise. A dynamic privilege (in the style of RESTORE_ADMIN) would also be defensible.

Suggested regression test: a user with no grants must receive ERROR 1142 from LOAD STATS for a payload naming a table they cannot access.

Impact:
Impact

An authenticated user with no privileges on the target table can replace that table's optimizer statistics.

TiDB's cost-based optimizer consumes these statistics cluster-wide. Setting a two-row table's row count to ~7.8×10⁸ causes systematically wrong plan selection — index ver
sus full scan, join order, and join algorithm — for every user querying that table, not only the attacker.

The target table is chosen by the contents of the loaded file, not by the statement, so any table in the cluster can be targeted by name.

This is reported as unauthorized modification of shared metadata, not as denial of service. The defect is the absent authorization check; it is demonstrated by direct
 contrast with four sibling statements that do enforce one.
